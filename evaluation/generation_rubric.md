# Generation Evaluation Rubric (FROZEN)

Approved and frozen before any final-test generation output was seen. Per
project convention: do not modify these definitions after seeing final-test
results. Any future change to this rubric must be logged as a new dated
version, not a silent edit -- this file should be treated the same as
`evaluation_questions_frozen.csv`: a hash-worthy artifact.

Scoring is **human-performed** (the researcher, informed by the frozen
`expected_answer`/`evidence_text` ground truth in `evaluation_questions_frozen.csv`),
not LLM-judged -- introducing a second, unvalidated model as grader would add
an entire unscoped methodology layer.

Raw execution logs (what the system did) and evaluation judgments (how it
was scored) are kept in SEPARATE files, never merged into one source of
truth -- see File Separation below.

---

## The five dimensions

### 1. Factual correctness
**Applies to:** answerable questions only, and only when the system actually
answered (not refused).
**Scale:**
- `Correct` -- all key facts in the answer match `expected_answer`
- `Partially Correct` -- some key facts correct, some missing or wrong
- `Incorrect` -- answer contradicts or misses the expected key facts
- `N/A` -- question is unanswerable by design, or the system refused

### 2. Groundedness / faithfulness
**Applies to:** RAG modes (B, C) only, and only when the system answered.
**Scale:**
- `Fully Grounded` -- every claim traces back to the provided context
- `Partially Grounded` -- some claims from context, others apparently from
  outside knowledge or unsupported by the given context
- `Not Grounded` -- claims are not supported by the provided context at all
- `N/A` -- Mode A (no context exists to be grounded in), or refused

**Distinction from #4 (deliberately not merged):** groundedness asks whether
a claim traces back to the *provided context*, regardless of whether that
context was itself correct. A model can be faithfully grounded in
misleading context (faithful-but-wrong) or ungrounded but accidentally
correct (unfaithful-but-right, e.g. Mode A drawing on real trained
knowledge). Collapsing these into one score would hide that distinction.

### 3. Refusal behaviour
**Applies to:** all modes. Mode A has no refusal instruction (Mode A's
prompt gives it no INSUFFICIENT_EVIDENCE protocol at all), so its scores
here are descriptive only -- not a fair comparison against B/C, which were
explicitly instructed.
**Scale:**
- `Correctly Answered` -- question was supported, system gave a substantive answer
- `Correctly Refused` -- question was unsupported, system said INSUFFICIENT_EVIDENCE (or equivalent)
- `Incorrectly Answered` -- question was unsupported, but system answered anyway (the dangerous case)
- `Incorrectly Refused` -- question was supported, but system refused anyway (coverage loss)

### 4. Hallucination count
**Applies to:** all modes, all questions (including refusals, which score 0
by definition -- a refusal makes no factual claims).
**Scale:** integer >= 0 -- count of distinct fabricated/unsupported factual
claims in the answer, judged against the frozen ground truth (Mode A) or
against the retrieved context (Modes B/C).
**Recorded alongside:** `hallucination_claim_notes` (free text) -- which
specific claims were flagged and why, for auditability of a subjective call.

### 5. Citation correctness
**Applies to:** RAG modes (B, C) only, and only when the system answered.
**Scale:**
- `Correct` -- cited URL(s) match both what was actually retrieved/used AND the verified expected source
- `Present-but-imprecise` -- a citation was given and matches something retrieved, but is not the verified correct source
- `Fabricated` -- cited a URL not actually present among the retrieved context chunks
- `Missing` -- system gave a substantive answer with no citation at all
- `N/A` -- Mode A, or refused

## Known frozen exceptions

**LDR-03** carries `exclusion_flag=conflict_case` (see `ambiguity_log.md`
entry #12: a genuine post-freeze source conflict, not a generation
failure). It is scored normally on all five dimensions like any other
question, but excluded from every primary aggregate metric and reported in
a separate table.

## File separation (raw execution vs. evaluation judgment)

**Execution log** (`generation_final_test_log.csv`) -- factual record of
what the system did. Written automatically by `run_generation_modes.py`.
Fields:
```
question_id, question, category, split, question_answerable, negative_type,
exclusion_flag, mode, top_k_chunk_ids, source_urls, retrieval_scores,
threshold_decision, prompt_sent, generated_answer, refused,
generation_latency_ms, retrieval_latency_ms, total_latency_ms,
execution_order_position
```

**Scoring template** (`generation_scoring_template.csv`) -- the execution
log's fields PLUS the rubric's blank judgment columns, generated by
`prepare_scoring_template.py` and filled in by hand. Added fields:
```
factual_correctness, groundedness_faithfulness, refusal_behaviour,
hallucination_claim_count, hallucination_claim_notes,
citation_correctness, scorer_notes
```

The execution log is never edited once written. All judgment happens in
the scoring template, which references but does not overwrite it.
